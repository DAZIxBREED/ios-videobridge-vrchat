# v0.1.1 Validation Procedure

**Candidate:** `0.1.1-dev.1`  
**Target release:** `v0.1.1`  
**Unity:** `2022.3.22f1`  
**Purpose:** Prove the Phase 1 stabilization changes before the final release tag is created.

The final `v0.1.1` tag must not be created until the required checks below are completed and the observed results are recorded. This procedure implements the release gate defined by `ROADMAP.md` and `docs/RELEASE_POLICY.md`.

## 1. Repository preflight

Generate the reproducible media fixtures:

```bash
./scripts/generate-test-media.sh
```

Run repository validation:

```bash
./scripts/validate-repository.sh
```

Expected:

- H.264 video fixture is detected.
- AAC audio fixture is detected.
- `yuv420p` pixel format is detected.
- HLS VOD playlist structure is valid.
- fixture SHA-256 checks pass.
- C# structural checks pass.
- runtime/package version strings match.
- no legacy playback-state names remain.

Record:

```text
Repository validation: PASS / FAIL
Commit tested:
Tester:
Date:
Notes:
```

## 2. Unity edit-mode tests

Set `UNITY` to the Unity 2022.3.22f1 executable and run:

```bash
UNITY="/path/to/Unity" ./scripts/run-unity-tests.sh
```

The suite must include the analyzer/redaction tests and `PlaybackStabilizationTests`.

Expected deterministic coverage includes:

- legal playback-state transitions accepted
- impossible direct transitions rejected
- absolute HTTPS source normalization
- rooted local path handling
- relative source rejection
- embedded credential rejection
- unsupported URL scheme rejection
- query-safe HLS detection
- negative seek clamp
- end-of-media seek clamp
- NaN/infinity seek rejection

## 3. Play Mode — normal VOD sequence

Use the generated `known-good-h264-aac.mp4` fixture.

Run this sequence:

1. **Load**
   - expected state: `Loading`
2. **Prepare**
   - expected: `Preparing -> Ready`
3. **Play**
   - expected state: `Playing`
4. **Pause**
   - expected state: `Paused`
5. Press **Prepare** while already prepared and paused
   - expected: state remains `Paused`
6. **Play** again
   - expected state: `Playing`
7. Seek backward beyond zero
   - expected target: `0`
8. Seek beyond the finite duration
   - expected target: approximately `duration - 0.05`
9. Enable **Loop VOD** and allow the file to reach its loop point
   - expected state: remains `Playing`
   - expected diagnostic event: `loop_iteration`
10. Disable loop and allow playback to complete
    - expected state: `Ready`
    - expected diagnostic event: `playback_completed`
11. **Stop**
    - expected state: `Stopped`
    - expected Unity `VideoPlayer.isPrepared`: false

Record:

```text
Normal VOD sequence: PASS / FAIL
Unexpected transitions:
Unexpected errors:
Notes:
```

## 4. Repeated load/unload stress

Repeat this sequence at least 10 times using the generated MP4:

```text
Load -> Prepare -> Play -> Pause -> Play -> Stop
```

Then repeat at least 10 times:

```text
Load A -> Prepare A -> immediately Load B -> Prepare B -> Stop
```

A and B may use the same redistributable fixture URL/path when only lifecycle churn is being tested.

Expected:

- no stale source metadata carries into the new load
- no unexpected `Ready` transition appears after a cancelled/failed preparation
- audio-track count resets between loads
- no unbounded coroutine/recovery growth
- no Unity exceptions

Record:

```text
Repeated load/unload: PASS / FAIL
Cycles completed:
Exceptions:
Notes:
```

## 5. Invalid-source handling

Verify the following are rejected without falling through into preparation or playback:

```text
media/video.mp4
ftp://example.com/video.mp4
https://user:password@example.com/video.mp4
```

Verify this remains a valid MP4 and is **not** classified as HLS solely because of query text:

```text
https://cdn.example/video.mp4?next=.m3u8
```

Expected:

- rejected values end in `Failed`
- Prepare/Play are not started by the harness after rejected Load
- credentials are not emitted to diagnostics
- the query-string HLS false positive does not occur

Record:

```text
Invalid-source handling: PASS / FAIL
Notes:
```

## 6. Preparation-timeout race test

Use a redistributable test endpoint/source that remains unresolved long enough to exceed the configured preparation timeout. Do not use a private or credential-bearing URL.

Expected:

1. state enters `Preparing`
2. timeout expires
3. Unity `VideoPlayer.Stop()` is invoked by the bridge
4. state becomes `Failed`
5. a late/stale `prepareCompleted` callback, if Unity delivers one, is ignored
6. state must **not** change from `Failed` back to `Ready` because of a stale callback
7. diagnostics contain `prepare_callback_ignored` if that late callback occurs

Record:

```text
Preparation timeout: PASS / FAIL
Timeout value:
Late callback observed: YES / NO
Final state:
Notes:
```

## 8. Application lifecycle — iOS device

Build and install the test application on an iPhone or iPad.

While VOD is playing:

1. note current media time
2. background the application
3. leave it backgrounded briefly
4. return to the application

Expected:

- lifecycle pause is logged as `application_paused`, not as a caller `playback_paused` event
- lifecycle resume is logged as `application_resumed`
- the bridge performs bounded reload/resume behavior when appropriate
- VOD resumes near the prior position
- state returns through recovery to `Playing` without an illegal transition

Repeat while preparation is active.

Expected:

- active preparation is cancelled on backgrounding
- state returns to `Loading`
- preparation restarts after foregrounding when appropriate
- stale preparation completion does not corrupt state

Record:

```text
iOS lifecycle: PASS / FAIL

iOS version:

```

## 9. Likely-live lifecycle smoke test

Using a redistributable HTTPS HLS live test stream:

1. Load and play the stream.
2. Background the application.
3. Foreground the application.

Expected:

- recovery does not try to restore a stale absolute VOD timestamp
- the backend is allowed to resume at its selected current/live position
- recovery remains bounded
- no infinite retry loop occurs

This is a Phase 1 smoke test only. Detailed HLS/live-edge engineering belongs to later roadmap releases.


## 10. Diagnostics inspection

Export diagnostics after the tests above.

Verify the log contains useful events for:

- state transitions
- prepare start/completion/timeout
- stale prepare callback rejection when observed
- seek requests/completions
- audio track discovery
- app pause/resume

Verify it does **not** expose:

- passwords
- access tokens
- signed query values targeted by the redactor
- cookies

## Final v0.1.1 release gate

The final release may be tagged only when:

- [ ] repository validation passes
- [ ] Unity edit-mode tests pass
- [ ] normal VOD Play Mode sequence passes
- [ ] repeated load/unload stress passes
- [ ] invalid-source handling passes
- [ ] preparation-timeout race passes
- [ ] audio-track/route reporting passes
- [ ] iOS background/foreground recovery passes
- [ ] likely-live lifecycle smoke test passes or is explicitly documented as a non-blocking environment limitation by a roadmap/release-policy compliant decision
- [ ] diagnostics inspection passes
- [ ] `CHANGELOG.md` is promoted from candidate notes to a dated `0.1.1` release entry
- [ ] package/runtime version is changed from `0.1.1-dev.1` to `0.1.1`
- [ ] the exact validated `main` commit is tagged `v0.1.1`

Until then, `0.1.1-dev.1` remains the current development candidate.
